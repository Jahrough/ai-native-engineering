# Contribution and documentation standards

## Scope and status

This repository is a learning framework. Keep proposals, examples, and verified implementations distinct. Use language such as **proposed**, **exercise**, **example**, or **verified** precisely; never imply that an exercise has been completed or a capability exists without evidence.

Do not modify or claim access to the suggested external practice repositories. Do not add application code, dependencies, infrastructure, or tooling unless a separate justified requirement calls for it.

## Writing standards

- Use clear Markdown headings, concise paragraphs, descriptive links, and tables where they improve comparison.
- Prefer actionable objectives and evidence-producing exercises over reading lists.
- Explain prerequisites and define specialized terms on first use or link to a reliable reference.
- Distinguish facts, assumptions, recommendations, and open questions. Avoid unsupported claims and fabricated outcomes.
- Prefer vendor-neutral concepts; label vendor-specific examples and link to current primary documentation.
- Cite authoritative, maintained sources. Prefer standards bodies, official technical documentation, peer-reviewed or primary research, and established operational references.
- Avoid duplicating content. Keep phase detail in its guide; link to shared policies in the cross-cutting documents.
- Keep links descriptive and relative for repository content. Verify that local links resolve.

## Changes and review

1. Inspect neighboring documentation and preserve its terminology and navigation.
2. Make the smallest complete change; update the index and cross-links when adding or moving content.
3. Check every phase guide against the common required sections: purpose, outcomes, objectives, prerequisites, competencies, concepts, exercises, project, deliverables, evaluation, dependencies, and resources.
4. Validate internal links, Markdown readability, and consistency of claims/status.
5. Have a reviewer assess correctness, safety, usefulness, and whether evidence is independently verifiable.

No Markdown linter or test framework is currently configured. For documentation-only changes, use the validation checklist above and any available repository checks; do not add tooling just for its own sake.
