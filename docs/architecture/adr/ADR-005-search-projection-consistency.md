# ADR-005: Search Projection Consistency and Conditional Writes

1. **Identifier and title:** ADR-005 - Search Projection Consistency and Conditional Writes
2. **Status:** PROPOSED
3. **Date:** 2026-11-05
4. **Decision owners:** TBD - Product Search owner and cross-system architecture owner
5. **Affected repositories:** product-search, product-catalog, platform-infrastructure, platform-gitops
6. **Context and problem statement:** Inbox deduplication handles known event IDs but does not atomically fence OpenSearch writes. Out-of-order or historical events can arrive after inbox cleanup, index loss, or replay. Physical deletes erase the version fence.
7. **Existing implementation and evidence:**
   - **CONFIRMED, static:** Search checks event IDs and highest inbox version; for create/update it reads OpenSearch and compares a document field. Delete does not follow the same document-version check. Evidence: product-search `src/main/java/dev/jahlopez/productsearch/listener/ProductEventConsumer.java`.
   - **CONFIRMED, static:** `ProductSearchService` sends ordinary index/delete requests with a fixed index and no explicit external version. Evidence: product-search `src/main/java/dev/jahlopez/productsearch/service/ProductSearchService.java`.
   - **CONFIRMED, static:** OpenSearch client is declared 2.17.0; infrastructure declares server 2.13. Conditional version behavior has not been integration-tested in this audit. Evidence: product-search `build.gradle.kts`; platform-infrastructure Terraform OpenSearch configuration.
8. **Decision drivers:** Atomic stale-write rejection at the projection; deterministic duplicate recovery; tombstone protection; explicit equal-version conflict detection; no cross-system exactly-once claim.
9. **Proposed decision:** Use OpenSearch strict external versioning for every live and tombstone document write, with the aggregate version as the external version. Lower versions are stale and must not overwrite. A version conflict is not automatically success: load/compare stored incarnation, version, event ID, and canonical fingerprint. Same-version same-event/fingerprint is a duplicate; same-version different identity/content is a conflict routed to the approved failure path. Do not use `external_gte` unless the system can prove identical content at equal versions. Represent delete as a versioned tombstone document and filter it from all queries. Restrict physical delete to a proven purge protocol.
10. **Alternatives considered:** Inbox-only guard (not atomic with OpenSearch and history may be pruned); application read-then-write check (racy); OpenSearch strict external versioning plus identity check (recommended); `external_gte` (simpler duplicate writes but masks conflicting payload); versioned physical deletes (server/client semantics require proof); tombstone document (retains fence).
11. **Trade-offs and consequences:** Every write and query path must understand tombstones and generations. A conflict requires an extra read and explicit classification. OpenSearch internal version metadata and document source version must be kept consistent. Concurrent requests must rely on the server's atomic conditional operation, not a check-then-write in Java.
12. **Failure modes and recovery behavior:** OpenSearch succeeds/inbox fails: redelivery gets a strict version conflict, compares stored identity/fingerprint, then records inbox only for an exact match. Inbox succeeds/offset commit fails: redelivery is a no-op only if the matching event/version remains valid. Lower version is skipped and recorded without deleting current state. Equal-version different event is a hard conflict, not acknowledged as duplicate. Delete writes tombstone at its version; an older update cannot resurrect it. Generation writes include epoch/generation fence and cannot mutate active generation after promotion.
13. **Security and operational considerations:** Restrict index/alias mutation to service identity and rebuild operator. Ensure deleted products are excluded from all search routes, facets, exports, and caches. Avoid logging sensitive event payloads on conflicts.
14. **Migration and compatibility implications:** New mapping/document metadata, conditional write requests, conflict classification, tombstones, query filters, and generation-aware aliases are required. Verify Java client/server pair and behavior for equal/lower version, conflicts, concurrent operations, tombstone writes, alias switch, and delete semantics in integration tests before relying on the guarantee.
15. **Dependencies on other ADRs:** ADR-001 identity/version; ADR-002 tombstone; ADR-003 generation rebuild; ADR-004 epoch; ADR-006 ack/replay; ADR-007 inbox/tombstone retention.
16. **Acceptance criteria:** Concurrent lower/higher writes never regress projection; exact duplicate after OpenSearch success/inbox failure is recognized; equal-version conflicting payload is surfaced; versioned deletion prevents replay resurrection; all query paths exclude tombstones; generation/epoch mismatch is rejected; integration tests run against the deployed OpenSearch version and declared Java client.
17. **Implementation ownership:** product-search owns writes, inbox, mapping, queries, and generation fencing; platform-infrastructure owns deployed OpenSearch version and access policies; Catalog owns version/event contract.
18. **Open questions:** Does the deployed server/client pair expose all required external version operations, including tombstone writes? What canonical event fingerprint serialization is stable across schema versions? How does alias promotion fence in-flight writers?
