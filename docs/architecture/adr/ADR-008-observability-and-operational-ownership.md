# ADR-008: Distributed-System Observability and Operational Ownership

1. **Identifier and title:** ADR-008 - Distributed-System Observability and Operational Ownership
2. **Status:** PROPOSED
3. **Date:** 2026-11-05
4. **Decision owners:** TBD - service owners, platform operations, SRE/observability owner
5. **Affected repositories:** product-catalog, product-search, platform-infrastructure, platform-gitops, platform-observability
6. **Context and problem statement:** Recovery and replay require observable progress across Catalog, PostgreSQL, Debezium, Kafka, consumers, inbox, OpenSearch generations, and the recovery authority. A repository named observability does not imply that telemetry infrastructure exists.
7. **Existing implementation and evidence:**
   - **CONFIRMED, static:** Infrastructure documents selected CloudWatch alarms/dashboard and EKS Container Insights. It also says no Prometheus scraper, long-term application metrics store, application dashboard, or trace backend is provisioned. Evidence: platform-infrastructure `OPERATIONS.md`.
   - **CONFIRMED, static:** GitOps README says Prometheus/Grafana and OpenTelemetry Collector/backend are not deployed. `platform-observability` tracks only a README. Evidence: platform-gitops `README.md`; platform-observability repository tree.
   - **UNVERIFIED:** Effective production telemetry, alert delivery, alert owners, and incident response were not tested.
8. **Decision drivers:** Detect loss before recovery becomes impossible; assign each metric to the component that knows it; minimize sensitive data in logs; route alerts to named responders; avoid creating a central service without a proven need.
9. **Proposed decision:** Keep instrumentation with the owning service/platform component and choose a shared backend only after ownership, retention, privacy, and cost are approved. Required signals include Catalog transaction/outbox failures; PostgreSQL slot lag/retained WAL; Debezium connector/task state; Kafka partition health and per-group lag; DLT count/age; consumer retry/failure rate; OpenSearch write/conflict/index health; projection drift; snapshot/rebuild progress and duration; generation/epoch disagreement; validation and alias promotion outcomes. Each signal needs source, labels/cardinality policy, dashboard, alert condition, runbook, severity, and accountable responder.
10. **Alternatives considered:** Rely on infrastructure logs alone (insufficient end-to-end progress); add a dedicated observability repository/platform immediately (cost and operational burden without confirmed requirements); owner-local metrics with a deliberately selected shared backend (recommended in stages); third-party SaaS (possible later after privacy/cost review).
11. **Trade-offs and consequences:** Shared telemetry improves correlation but creates cost, access, retention, and availability dependencies. High-cardinality IDs must not become metric labels. `platform-observability` may be assigned implementation later, but it currently contains no implementation.
12. **Failure modes and recovery behavior:** Missing telemetry cannot be treated as healthy. Connector/authority status unknown, stale offsets, or absent alert pipeline must be surfaced as unknown/degraded. Every recovery runbook records event/offset/generation/epoch identifiers in protected operational records, not in public logs.
13. **Security and operational considerations:** Redact payloads and secrets; protect DLT and recovery dashboards; use least-privilege queries; set log/metric retention with ADR-007; audit manual replay, epoch advance, and alias promotion.
14. **Migration and compatibility implications:** Add instrumentation where source truth exists, platform exporters/backends only after explicit owner and security review, alert routes and runbooks, and tests for alert firing and silence. Do not add a backend solely to satisfy this ADR.
15. **Dependencies on other ADRs:** ADR-003 rebuild signals; ADR-004 authority transition; ADR-005 projection conflicts; ADR-006 retries/DLT; ADR-007 retention/capacity.
16. **Acceptance criteria:** Each critical failure scenario has an observable signal and named responder; dashboard values reconcile with authoritative component state; alerts are tested end to end; missing/stale telemetry is distinguishable from healthy zero; runbooks identify safe actions and prohibited destructive recovery steps; sensitive payloads are absent from telemetry.
17. **Implementation ownership:** product-catalog owns application/outbox metrics; product-search owns consumer/inbox/index/rebuild metrics; platform-infrastructure owns DB/Connect/Kafka/managed-service signals; platform-gitops owns rollout health and deployment guards; platform-observability ownership is TBD until a team accepts it.
18. **Open questions:** Who owns the observability repository/platform? Which backend is approved and funded? Who receives and acknowledges alerts? What telemetry retention and data classification apply? Which signals are contractual production readiness blockers?
