# ADR-002: Durable Deletion and Tombstones

1. **Identifier and title:** ADR-002 - Durable Deletion and Tombstones
2. **Status:** PROPOSED
3. **Date:** 2026-11-05
4. **Decision owners:** TBD - Catalog domain/privacy owner and Search owner
5. **Affected repositories:** product-catalog, product-search, platform-infrastructure, platform-gitops
6. **Context and problem statement:** A delete event carries a higher version, but Catalog physically removes the product. Search physically deletes the OpenSearch document. If an old event is replayed after inbox history or the document is lost, there may be no durable version fence to prevent resurrection.
7. **Existing implementation and evidence:**
   - **CONFIRMED, static:** `ProductService.deleteProduct` emits a next-version `DELETED` event and deletes the product row in the same service transaction. Evidence: product-catalog `src/main/java/dev/jahlopez/productcatalog/service/ProductService.java`.
   - **CONFIRMED, static:** Search's deletion handler calls OpenSearch physical delete; no external version is included in the request. Evidence: product-search `src/main/java/dev/jahlopez/productsearch/listener/ProductEventConsumer.java`; `src/main/java/dev/jahlopez/productsearch/service/ProductSearchService.java`.
   - **PARTIALLY CONFIRMED:** Search inbox retains event/version records, but retention is not established in inspected application sources. External backups/replay horizons are unknown.
8. **Decision drivers:** Prevent resurrection after duplicate or historical replay; preserve a source for complete Search rebuild; minimize retained personal/commercial data; support finite retention only when a safe purge condition is provable.
9. **Proposed decision:** Represent deletion as durable source state rather than immediate loss of all aggregate identity. A tombstone should minimally retain aggregate ID, incarnation if applicable, final positive version, deletion event ID, canonical event fingerprint, deletion time, and a deletion marker. It must not retain product fields unless business/legal requirements require them. Search stores a versioned tombstone document and filters it from every user-facing query. Physical removal is an optimization only after ADR-007 retention/recovery horizons and a replay fence are satisfied.
10. **Alternatives considered:** Physical delete only (smallest schema, unsafe without durable fence); retain full deleted product (simple rebuild, unnecessary data exposure); retain minimal tombstone (recommended balance); rely only on inbox rows (purge/restore and projection loss can remove the fence).
11. **Trade-offs and consequences:** Tombstones add storage and API/query obligations. Minimal tombstones reduce data retention but complicate rebuild sources if a deletion is needed to prevent replay. Indefinite tombstone retention is not assumed; any purge requires a proven upper bound on replay, backup restoration, and rebuild history or another durable fence such as a monotonic recovery epoch plus source reconciliation.
12. **Failure modes and recovery behavior:** Replayed lower-version update cannot replace a tombstone; same-version conflicting event is quarantined; a recreated product requires a new ID or approved incarnation. If tombstone history is missing after restore, fail closed and rebuild from an authoritative source before serving writes or promoting Search.
13. **Security and operational considerations:** Apply data minimization, access control, and deletion audit controls. Tombstone metadata can still be personal or linkable data; privacy/legal owner must approve fields and retention. Ensure search filters cover every API route, aggregations, and exports.
14. **Migration and compatibility implications:** Catalog schema and API/service paths need soft-delete/tombstone state and unique-ID constraints; Search document mappings and query filters must change; event schema must carry deletion/incarnation identity. Migrate existing physically deleted history only if an authoritative source exists; do not invent missing tombstones.
15. **Dependencies on other ADRs:** ADR-001 identity/incarnation/version; ADR-003 rebuild source; ADR-005 Search representation; ADR-007 purge and recovery horizon.
16. **Acceptance criteria:** Delete persists a versioned minimal source tombstone atomically with the outbox event; all Search queries exclude tombstones; stale update replay cannot resurrect a deleted product; same-ID recreation follows an approved rule; retention purge is rejected unless documented recovery/replay horizons and fencing are satisfied; privacy review approves fields and retention.
17. **Implementation ownership:** product-catalog owns durable delete state; product-search owns tombstone projection/filtering; infrastructure owns backup/retention mechanisms; business/privacy owners approve purge policy.
18. **Open questions:** What is the legal/business deletion obligation? Which fields must be erased immediately? Is an opaque ID plus version permissible to retain? What is the maximum supported historical replay/restore horizon?
