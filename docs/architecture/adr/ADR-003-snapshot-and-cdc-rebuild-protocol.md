# ADR-003: Snapshot and CDC Projection Rebuild Protocol

1. **Identifier and title:** ADR-003 - Snapshot and CDC Projection Rebuild Protocol
2. **Status:** PROPOSED
3. **Date:** 2026-11-05
4. **Decision owners:** TBD - Search, database, Kafka, and platform architecture owners
5. **Affected repositories:** product-catalog, product-search, platform-infrastructure, platform-gitops, platform-observability
6. **Context and problem statement:** Search is a derived OpenSearch projection. A complete index-loss or rebuild procedure must combine a Catalog snapshot and ongoing CDC without missing committed changes or letting stale snapshot rows overwrite newer events. Kafka offsets and a PostgreSQL snapshot are not one distributed atomic snapshot.
7. **Existing implementation and evidence:**
   - **CONFIRMED, static:** Connector config names a slot/publication and routes the outbox to `product-events`; no explicit snapshot mode or topic retention/topology contract is present in that JSON. Evidence: platform-infrastructure `connectors/postgres-outbox-connector.json`.
   - **CONFIRMED, static:** Operations says connector registration/sync is manual and cautions against slot/offset reset. Evidence: platform-infrastructure `OPERATIONS.md`.
   - **NOT IMPLEMENTED IN INSPECTED SOURCE:** No Search generation/alias rebuild protocol or Catalog snapshot export contract was found in the cited application paths.
   - **UNVERIFIED:** Broker topic identity, partition count, transaction visibility, offset retention, connector continuity, and production snapshot behavior.
8. **Decision drivers:** No committed mutation is omitted under stated assumptions; each generation is isolated; duplicates and stale writes are harmless; uncertainty aborts safely; promotion is auditable and reversible only to a still-current generation.
9. **Proposed decision:** Use a new isolated Search generation. Verify CDC continuity and the stable topic identity/partition set. Capture the next-to-read broker end-offset vector `E[p]` for every partition using the same visibility/isolation semantics as the rebuild consumer; explicitly decide whether transactional records are read committed. Then begin a read-only PostgreSQL `REPEATABLE READ` snapshot and export every live aggregate plus durable tombstones with incarnation and version. Start a generation consumer explicitly at `E[p]`; it may run concurrently with export only through the same conditional versioned writer used by snapshot rows. Validate source/projection invariants and catch-up before alias promotion. Record generation ID, recovery epoch, topic identity/partition set, offset vector, snapshot identity, and validation evidence. Abort rather than guess when any fence is missing or continuity is uncertain.
10. **Alternatives considered:** Stop writes/CDC for the whole rebuild (simple but disrupts service and still requires ordering proof); snapshot first then begin CDC (gap risk); consume CDC from earliest plus snapshot with version guards (potentially large replay); proposed offset-before-snapshot protocol (bounded replay if assumptions hold); periodic full reconciliation (useful but not a substitute for a lost source).
11. **Trade-offs and consequences:** The offset vector is partition-local, not globally atomic. Correctness requires: (a) every committed outbox insert is eventually published after commit; (b) offsets are captured as consumer-visible next positions under the same isolation semantics used for replay; (c) no event becomes visible at an offset below the captured `E` after capture; (d) all relevant partitions are included and their identity/topology remains stable; (e) connector slot/WAL continuity is maintained; (f) snapshot rows include deletion fences; (g) both snapshot and CDC use atomic per-document conditional versioning; and (h) the offset vector remains readable. A long PostgreSQL snapshot may retain old row versions and increase vacuum/storage pressure. A publication delayed past `E` for a pre-snapshot commit is harmless only because that commit appears in the later snapshot; the delayed record may be stale, equal, or newer than the snapshot row and must be classified by version and event identity.
12. **Failure modes and recovery behavior:**
   - Commits before offset capture are represented by the later snapshot, whether or not their event is already visible in Kafka; the snapshot must be established after capture and include the commit. Already-published records before `E` are not replayed into the generation.
   - Commits between capture and snapshot establishment are included in the snapshot; their later CDC records are consumed after `E` and must be deduplicated/version-checked.
   - Commits during export are excluded from the fixed snapshot but must be published after `E`; snapshot/CDC writes race safely only with atomic conditional version checks.
   - A transaction open at snapshot start is excluded if it commits after the snapshot; its post-commit event must be after `E`. If it committed before snapshot establishment but publication is delayed, the snapshot contains it and later CDC is stale/equal/newer according to subsequent mutations; the conditional writer must safely classify each case.
   - Connector restart is acceptable only if the same source offsets/slot continuity and topic identity are proven. Slot loss, required WAL removal, topic recreation/partition change, offset expiration, or unknown transaction-visibility semantics aborts this generation and requires a fresh fence/snapshot.
   - Interrupted snapshot/export does not promote. Resume only if the exact PostgreSQL snapshot remains valid and CDC fence is intact; otherwise discard the isolated generation and restart.
   - Before alias promotion, stop/fence competing generation writers, verify every expected partition caught up to a recorded high-water mark, validate counts/version/tombstone invariants against the snapshot/source, and atomically switch the alias. A retained old index is not rollback-ready unless it remains current or is caught up.
13. **Security and operational considerations:** Snapshot export is read-only and least-privileged. Protect generation controls and alias changes. Track snapshot age, WAL retention, connector state, per-partition offsets/lag, validation failures, and promotion operator. Do not expose product data in metrics.
14. **Migration and compatibility implications:** Requires a Catalog snapshot/export interface, versioned tombstones, Search generation/index alias writer, topic/offset metadata persistence, and GitOps orchestration/fencing. OpenSearch external-version semantics and conflict response must be verified against deployed server/client versions before relying on them.
15. **Dependencies on other ADRs:** ADR-001 identity/version; ADR-002 deletion state; ADR-004 epoch; ADR-005 conditional writes; ADR-006 consumer offset semantics; ADR-007 retention/WAL objectives; ADR-008 telemetry.
16. **Acceptance criteria:** Controlled tests prove the commit timelines above; E is captured for all stable partitions and consumers seek explicitly; duplicates and out-of-order writes converge; connector restart with continuity succeeds; slot/WAL loss, topic change, and expired offsets abort; snapshot failure cannot promote; projection validation detects missing/extra/version/tombstone mismatches; alias promotion is fenced and auditable; old generation rollback is allowed only after freshness is proven.
17. **Implementation ownership:** product-catalog owns stable snapshot/export and tombstone fields; platform-infrastructure owns Kafka/Connect/DB continuity prerequisites; product-search owns generation writer/validation; platform-gitops owns authorized orchestration; platform-observability owns no implementation until explicitly assigned.
18. **Open questions:** Does Kafka expose a durable topic identity usable by the rebuild controller? How will all-partition end offsets be captured and persisted with the consumer's isolation semantics? How long may a repeatable-read snapshot run? Which Catalog isolation/export API is supportable? What exact evidence proves connector continuity? How are Kafka Connect transactional visibility and aborted records handled?
