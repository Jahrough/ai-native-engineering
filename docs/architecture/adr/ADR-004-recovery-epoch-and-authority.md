# ADR-004: Recovery Epoch and Disaster-Recovery Authority

1. **Identifier and title:** ADR-004 - Recovery Epoch and Disaster-Recovery Authority
2. **Status:** PROPOSED
3. **Date:** 2026-11-05
4. **Decision owners:** TBD - platform recovery owner, security owner, Catalog/Search owners
5. **Affected repositories:** ai-native-engineering, product-catalog, product-search, platform-infrastructure, platform-gitops, platform-observability
6. **Context and problem statement:** Catalog PITR may restore an older version and event history. Search, Kafka, and GitOps may still contain newer state. A monotonic recovery authority must not be rolled back with Catalog or inferred from desired deployment files.
7. **Existing implementation and evidence:**
   - **CONFIRMED, static:** GitOps stores desired Kubernetes configuration; infrastructure docs distinguish Terraform ownership and GitOps ownership. No recovery epoch authority or service enforcement was found in inspected sources.
   - **CONFIRMED, static:** Infrastructure documents seven-day RDS backup retention and says cross-region replication/failover are not provisioned. Evidence: platform-infrastructure `OPERATIONS.md`; `terraform/modules/database/main.tf`.
   - **UNVERIFIED:** No live recovery register, backup independence, or production restoration procedure was exercised.
8. **Decision drivers:** Epoch must survive Catalog PITR; updates require authorization and audit; no continuous custom service unless necessary; disagreement must fail closed; partial transitions must resume without decrementing epoch.
9. **Proposed decision:** Use a protected external monotonic recovery register as the authority, with conditional compare-and-advance and independently retained audit evidence. GitOps contains a desired-state mirror and pre-sync validation only; it is not the authority. Catalog stores a mirror for diagnostics, not authorization. Every outbox event carries the Catalog mirror epoch allocated in the same transaction as its mutation; Search compares it with the authoritative active epoch and rejects stale/mismatched events. Each Search generation is bound to an epoch and cannot be promoted under another epoch. Prefer an existing managed control-plane record with access controls and durable audit rather than introducing a continuously running recovery service. The exact product (object/record/control plane), authorization quorum, independent backup, and disaster procedure require owner/security approval.
10. **Alternatives considered:** GitOps-only state (easy review but can be restored/reverted); protected external record with conditional update (recommended, no service process required); dedicated recovery service (strong policy enforcement but extra deployment/availability/cost); deriving epoch from timestamps or Kafka offsets (not a durable authority).
11. **Trade-offs and consequences:** External register is a new operational dependency and must be protected against accidental rollback. If the register itself is restored from an older backup, it cannot prove the previously highest epoch by itself. Fail closed, freeze restore/rebuild/promotion, compare against an independently retained append-only audit/replica or provider audit evidence, and require authorized reconciliation that advances above the greatest verified epoch. If no independent evidence can establish a safe floor, recovery remains blocked; never silently accept the lower value. A total rollback of every authority copy is not solvable by software in this design and is an explicit residual risk.
12. **Failure modes and recovery behavior:**
   - States: `ACTIVE(e)` -> `PREPARING(e+1, transitionId)` -> `CATALOG_RESTORED(e+1)` -> `SEARCH_GENERATION_VALIDATED(e+1)` -> `ACTIVE(e+1)`.
   - Begin only with authorized transition record and preserved old epoch. Quiesce or fence normal writes/indexing as defined by runbook. Restore Catalog; reconcile its local mirror to the authoritative pending epoch. Build Search generation bound to the same epoch. Validate then commit `ACTIVE(e+1)`.
   - If interrupted, retain `PREPARING` and resume forward after verifying artifacts. Do not decrement or reuse `e`; abandon by advancing to a new epoch if evidence requires a restart. No component serves or promotes data on missing authority, invalid signature/record, or mismatch.
   - GitOps pre-sync rejects a manifest whose epoch is lower than or inconsistent with the authority. It cannot advance the authority by ordinary sync.
   - Search-only restoration/rebuild uses a new generation within the currently active Catalog recovery epoch; it does not increment Catalog's epoch unless source-of-truth history was also restored backward.
13. **Security and operational considerations:** Separate read and advance permissions; require multi-party approval for destructive Catalog PITR; use immutable/audited change records, break-glass alerting, least privilege, and periodic restore tests. Define who can reconcile a register rollback.
14. **Migration and compatibility implications:** Add authority integration to restore workflow, Catalog mirror, outbox/event epoch field, Search event validation and generation metadata, and GitOps pre-sync guard. Roll out enforcement in observe-only mode only if owner-approved; before mandatory fail-closed enforcement, initialize and reconcile the authority and all mirrors. Strict v1 schema validation means epoch-field introduction needs an explicit compatible producer/consumer rollout.
15. **Dependencies on other ADRs:** ADR-003 rebuild protocol; ADR-005 Search epoch/version enforcement; ADR-006 replay epoch validation; ADR-007 recovery objectives; ADR-008 alert ownership.
16. **Acceptance criteria:** PITR to an older Catalog backup cannot decrease the authority; unauthorized advance and stale GitOps sync are rejected; mismatches stop affected writes/promotion; partial transitions are idempotently resumed; register-backup rollback is detected and requires independent reconciliation; Search-only rebuild leaves active epoch unchanged; every transition is attributable and audited.
17. **Implementation ownership:** platform-infrastructure owns the protected record resource and audit/backup properties; platform-gitops owns desired mirror and pre-sync guard; product-catalog owns its non-authoritative mirror; product-search enforces epoch on events and generations; named recovery operator owns procedures.
18. **Open questions:** What managed record provides conditional monotonic updates and independent audit? Who may advance, with what quorum? Which audit/backup source is independent of register restoration? What happens operationally when authority is unavailable? Which transition steps quiesce writes?
