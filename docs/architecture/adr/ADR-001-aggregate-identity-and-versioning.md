# ADR-001: Aggregate Identity and Versioning

1. **Identifier and title:** ADR-001 - Aggregate Identity and Versioning
2. **Status:** PROPOSED
3. **Date:** 2026-11-05
4. **Decision owners:** TBD - Catalog domain owner and cross-system architecture owner
5. **Affected repositories:** product-catalog, product-search, platform-infrastructure, platform-gitops
6. **Context and problem statement:** Search needs a stable identity and strictly monotonic per-aggregate version to order events and prevent stale replay. Product IDs are generated database IDs today, while deletion removes the source row. Reuse and incarnation policy is not established.
7. **Existing implementation and evidence:**
   - **CONFIRMED, static:** Catalog uses a generated `Long` primary key and a unique SKU; `Product.version` is `Integer`. `ProductService` locks rows for update/delete and increments update versions. Delete emits `nextVersion()` then physically deletes the row. Evidence: product-catalog `src/main/java/dev/jahlopez/productcatalog/model/Product.java` (`id`, `sku`, `version`, `nextVersion`); `src/main/java/dev/jahlopez/productcatalog/service/ProductService.java` (`updateProduct`, `deleteProduct`); `src/main/java/dev/jahlopez/productcatalog/repository/ProductRepository.java` (`findByIdForUpdate`).
   - **CONFIRMED, static:** V2 migration converts product version from `BIGINT` to `INTEGER` and constrains it to 1..2147483647. Evidence: product-catalog `src/main/resources/db/migration/V2__enforce_product_versions_and_outbox_constraints.sql`.
   - **CONFIRMED, static:** Event schema v1 requires positive integer `version` and numeric `productId`; compatibility enforcement across producer and consumer releases was not found. Evidence: product-search `src/main/resources/schemas/product-event-v1.schema.json`.
   - **UNVERIFIED:** Actual external ID allocation/reuse behavior across restore, import, and administrative tooling is not established by these files.
8. **Decision drivers:** No stale event may resurrect an earlier incarnation; versions must not wrap or silently regress; source mutation and version allocation must serialize; migrations must safely handle existing rows and events; event consumers must be able to compare versions.
9. **Proposed decision:** Use a positive signed 64-bit monotonically increasing version per aggregate, allocated atomically with every mutation and delete. Never reuse an aggregate ID, including after Catalog PITR. The current database identity sequence alone does not establish that guarantee after a restore; either use a non-repeating identifier strategy or preserve a separately protected allocation high-water mark and reconcile it before writes resume. If business requirements require same-ID recreation, add an explicit immutable incarnation identifier and compare `(incarnation, version)` under a separately approved ordering rule; do not infer a new incarnation from a reset version. Preserve the last event ID and a canonical payload fingerprint with the aggregate's durable lifecycle state. Overflow or invalid/non-positive version state must fail the write and alert; do not wrap or reset. Migrate database, Java model, JSON contract, and consumer storage with an expand/contract rollout and compatibility window.
10. **Alternatives considered:** Keep 32-bit versions (low migration cost, bounded lifetime); use timestamps (clock skew and ties); reuse IDs with reset versions (historical replay can resurrect); permit reuse with incarnation (more robust but adds domain and contract complexity).
11. **Trade-offs and consequences:** Wider versions increase schema and compatibility work but remove the known 32-bit ceiling. Never-reuse IDs simplify ordering, but a product/SKU business rule may conflict. Incarnation adds complexity and must be carried by all events, inbox rows, and Search documents.
12. **Failure modes and recovery behavior:** Concurrent changes must serialize on the aggregate row or an equivalent database constraint. Overflow, duplicate `(aggregate, incarnation, version)`, or an attempted ID reuse must fail closed. PITR that restores an older version requires ADR-004 recovery fencing; it must not authorize version reuse.
13. **Security and operational considerations:** Restrict administrative identity changes and imports. Audit any exceptional identity repair. Do not include sensitive product data in event fingerprints; use a deterministic digest of canonical event fields.
14. **Migration and compatibility implications:** Expand producer/consumer readers before emitting 64-bit or incarnation fields; preserve old schema handling during rollout. Backfill existing rows/events consistently, validate max values and uniqueness, then contract old integer paths only after all consumers are upgraded. The v1 schema's integer range and unknown-field rejection make coordinated compatibility work necessary.
15. **Dependencies on other ADRs:** ADR-002 deletion state; ADR-003 rebuild ordering; ADR-005 Search conditional writes; ADR-006 replay; ADR-007 retention.
16. **Acceptance criteria:** Database and application represent signed 64-bit positive versions end to end, bounded at 9223372036854775807; concurrent update tests prove a unique contiguous or otherwise explicitly permitted monotonic sequence; overflow fails without mutation/outbox divergence; migration tests cover existing data and rollback/forward strategy; contract tests exercise old/new producer-consumer combinations; ID allocation cannot reuse an ID after PITR; ID reuse and incarnation cases have explicit domain-approved tests.
17. **Implementation ownership:** product-catalog owns aggregate persistence and outbox payload; product-search owns event and inbox compatibility; platform-infrastructure owns database operational prerequisites; canonical decision remains here.
18. **Open questions:** Is SKU reuse allowed after deletion? Which non-repeating ID strategy or independently protected allocation high-water mark will survive PITR? Is product ID reuse possible through imports or restore? Does the business need same-ID recreation? Who approves exceptional repair? Which canonicalization is used for event fingerprints?
