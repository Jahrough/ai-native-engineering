# ADR-006: Kafka Consumer Acknowledgment and DLT Semantics

1. **Identifier and title:** ADR-006 - Kafka Consumer Acknowledgment and DLT Semantics
2. **Status:** PROPOSED
3. **Date:** 2026-11-05
4. **Decision owners:** TBD - Search owner, Kafka/platform owner, operations owner
5. **Affected repositories:** product-search, platform-infrastructure, platform-gitops, platform-observability
6. **Context and problem statement:** Kafka, Search PostgreSQL inbox, and OpenSearch cannot commit atomically under the inspected configuration. Multiple listener groups consume the source topic; poison events and DLT routing therefore have group-specific behavior.
7. **Existing implementation and evidence:**
   - **CONFIRMED, static:** General and indexing listeners have separate groups; a poison-pill SKU throws in the general listener. The DLT listener logs the record. Evidence: product-search `src/main/java/dev/jahlopez/productsearch/listener/ProductEventConsumer.java`.
   - **CONFIRMED, static:** A bounded exponential backoff and `DeadLetterPublishingRecoverer` are configured. Evidence: product-search `src/main/java/dev/jahlopez/productsearch/config/KafkaConsumerConfig.java`.
   - **PARTIALLY CONFIRMED:** `spring-kafka` has no direct version in Gradle; Spring dependency management may resolve it. Effective version, effective ack mode, auto-commit, and transaction manager were not resolved or runtime-tested. Evidence: product-search `build.gradle.kts`; application configuration and listener factory.
8. **Decision drivers:** Make offset commit ordering explicit; preserve source record identity; avoid hidden listener-group coupling; keep poison messages from blocking healthy partitions indefinitely; ensure replay re-enters validation/fencing.
9. **Proposed decision:** Define consumer behavior as at-least-once. Resolve and record the actual Spring Kafka version. Explicitly disable Kafka auto-commit and select/document a container acknowledgment mode that commits a record only after listener processing returns successfully. Do not claim Kafka transactions make OpenSearch or PostgreSQL atomic. Publish DLT with original bytes and source topic/partition/offset, consumer group, listener identity, event ID when parseable, recovery epoch, attempt/failure metadata, and timestamp. If DLT publication fails, do not advance the source offset. DLT consumption is inspection/metrics only; authorized replay must re-enter the normal source validation path and preserve event ID, version, and epoch checks. Clarify whether the general listener group is required; remove or isolate simulated poison behavior from production records.
10. **Alternatives considered:** Auto-commit (unsafe ambiguity); per-record ack (clear but may reduce throughput); batch ack (higher throughput but larger replay window); manual ack (more control, more failure states); Kafka transaction around Kafka-only offset/DLT (does not include OpenSearch/PostgreSQL); automatic DLT replay (risks loops and bypasses operator controls).
11. **Trade-offs and consequences:** At-least-once permits duplicates and requires idempotent handlers. DLT is another durable operational queue with retention, ownership, and replay safeguards. Separate groups intentionally process independently; one group's success does not imply another's success. If one fails, the other may continue and the failed group may later retry/DLT the same source record.
12. **Failure modes and recovery behavior:**
   1. OpenSearch succeeds, inbox write fails: source offset remains retryable; redelivery must be recognized through conditional projection identity/version.
   2. Inbox succeeds, offset commit fails: redelivery must be an inbox/projection no-op.
   3. DLT publish fails: source offset must not be committed; retry publication and alert.
   4. DLT publish succeeds, source offset commit fails: duplicate DLT is possible; DLT identity and deduplication must preserve source coordinates.
   5. Multiple groups process one record: each has independent offsets and outcomes.
   6. One group succeeds while another fails: record both outcomes; do not treat source-wide completion as atomic.
13. **Security and operational considerations:** DLT payloads may contain sensitive catalog data. Restrict read/replay permissions, audit operator and reason, encrypt records, protect replay tooling, cap/alert on age and count, and never print payloads to logs. Poison test data must be confined to tests or explicitly gated non-production fixtures.
14. **Migration and compatibility implications:** Explicit consumer properties and acknowledgment semantics; possible listener consolidation or purpose documentation; DLT envelope/header contract; replay command/runbook with authorization; compatibility tests must include malformed bytes and schema versions. Kafka transaction manager only if a Kafka-to-Kafka atomic operation is justified.
15. **Dependencies on other ADRs:** ADR-001 event identity/version; ADR-003 rebuild offsets; ADR-004 epoch validation; ADR-005 projection idempotency; ADR-007 DLT/source retention; ADR-008 alerting/ownership.
16. **Acceptance criteria:** Effective dependency version and ack/commit behavior are observable; all six crash windows are failure-injection tested; DLT publication failure does not lose source record; duplicate DLT retains source identity and cannot cause unsafe replay; authorized replay re-enters validation/version/epoch fencing; separate group behavior is documented and tested.
17. **Implementation ownership:** product-search owns listeners/error handling/replay interface; platform-infrastructure owns topic/DLT provisioning and Kafka policy; platform-gitops deploys approved settings; operations owns authorization and review process.
18. **Open questions:** Is the general listener a production requirement or obsolete demonstration? Which groups are business-critical? Who can replay and approve? Should replay republish to the original topic or use a controlled replay topic? What is acceptable DLT retention?
